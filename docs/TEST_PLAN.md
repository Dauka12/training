# План тестирования

## Регистрация
### Успешная регистрация
- Given гость на странице регистрации с локалью `ru`
- When он вводит валидный email, сложный пароль и отправляет форму
- Then создается пользователь с ролью `user`, неподтвержденным email, hashed password, hashed verification token и отправляется письмо верификации

### Ошибка при повторном email
- Given уже существует пользователь с таким email
- When гость повторно отправляет форму регистрации
- Then API возвращает контролируемую ошибку валидации без раскрытия лишних данных

### Ограничение частоты
- Given с одного IP были многократные попытки регистрации
- When лимит превышен
- Then API возвращает `rate_limited`

## Верификация email
- Given пользователь получил ссылку верификации
- When он отправляет валидный токен
- Then email помечается как подтвержденный, токен становится недействительным, пользователь может войти

- Given токен просрочен или неверен
- When пользователь отправляет токен
- Then API возвращает безопасную ошибку без утечки деталей

## Логин
- Given пользователь с подтвержденным email и корректным паролем
- When он отправляет форму логина
- Then создается безопасная сессия, выставляется cookie и возвращается профиль

- Given email не подтвержден
- When пользователь пытается войти
- Then логин отклоняется с локализованным сообщением

## Выход
- Given у пользователя есть активная сессия
- When он нажимает выход
- Then сервер отзывает сессию и cookie очищается

## Восстановление пароля
- Given пользователь отправил email для восстановления
- When email существует
- Then создается hashed reset token и отправляется письмо

- Given email не существует
- When отправлен запрос восстановления
- Then ответ остается нейтральным и не раскрывает существование аккаунта

## Сброс пароля
- Given пользователь имеет валидный reset token
- When отправляет новый валидный пароль
- Then пароль меняется, токен инвалидируется, старые сессии отзываются

## Онбординг
- Given пользователь впервые вошел
- When он заполняет все обязательные поля анкеты и сохраняет
- Then профиль нормализуется и сохраняется, доступность и оборудование привязываются к пользователю

- Given пользователь указывает невалидные диапазоны роста, веса или длительности
- When форма отправляется
- Then сервер отклоняет запрос по валидации

## Генерация начального плана
- Given профиль пользователя завершен и каталог заполнен seed-данными
- When пользователь запускает генерацию начального плана
- Then backend детерминированно считает калории, макросы и воду, формирует privacy-safe AI payload, валидирует JSON-ответ AI и сохраняет новую версию плана

## Валидация AI-ответа
- Given AI вернул exercise_id вне candidate_exercises
- When backend валидирует ответ
- Then генерация отклоняется и выполняется не более одного безопасного ретрая

- Given AI вернул не-JSON или нарушил locale/schema contract
- When backend обрабатывает ответ
- Then ответ не сохраняется, лог генерации фиксируется как ошибка

## Today Dashboard
- Given у пользователя есть активный план и логи за сегодня
- When он открывает экран Today
- Then отображаются сегодняшняя тренировка, статус питания, прогресс воды, быстрые действия, прогресс недели, тренд веса, следующая сессия, план health и краткая сводка уведомлений

## Логирование тренировки
- Given на сегодня запланирована тренировка
- When пользователь отмечает `done`, `partially_done`, `skipped` или `rescheduled`
- Then создается workout log с pain flag, difficulty, timestamp и связью с plan version

## Логирование питания
- Given пользователь находится на экране Track
- When он отмечает `followed`, `partially_followed` или `off_plan`
- Then создается meal log и обновляется дневная сводка соблюдения

## Логирование воды
- Given у пользователя есть hydration target
- When он нажимает quick-add `250ml` или `500ml` либо вводит custom значение
- Then создается water log и прогресс за день обновляется детерминированно

## Напоминания о воде
- Given у пользователя включены hydration reminders
- When наступает подходящее время и дневная цель еще не достигнута
- Then создается in-app notification и email только если это разрешено настройками

## Check-in веса
- Given пользователь отправляет еженедельный check-in
- When вес, энергия и соблюдение заметно отклоняются
- Then система фиксирует weekly check-in и может выставить trigger на адаптацию

## Пропуск тренировки и рескедулинг
- Given пользователь пропустил тренировку
- When backend вычисляет перенос
- Then выбирается следующий допустимый слот без очевидно плохого восстановления либо выставляется adaptation review

## Еженедельный check-in и регенерация
- Given выполнены условия регенерации
- When check-in обработан
- Then создается новая версия плана, старая версия superseded, история и старые логи сохраняются

## Переключение локали
- Given пользователь использует `ru` по умолчанию
- When он переключает язык на `kk`
- Then UI, серверные сообщения и AI generated plan text используют `kk`, а выбор сохраняется

## Переключение темы
- Given пользователь использует системную тему впервые
- When он выбирает `dark` или `light`
- Then тема применяется и сохраняется на устройстве или в профиле

## Центр уведомлений
- Given у пользователя есть непрочитанные уведомления
- When он открывает notification center и отмечает уведомление прочитанным
- Then unread counter уменьшается и статус сохраняется

## Кабинет тренера
- Given пользователь назначен тренеру
- When тренер открывает список подопечных
- Then он видит только назначенных пользователей, их adherence и может оставить заметку или инициировать регенерацию

## Админ и каталоги
- Given администратор авторизован
- When он создает или редактирует оборудование и упражнения
- Then изменения валидируются, попадают в каталог и журнал аудита

## Support ticket reply flow
- Given пользователь создал приватный тикет
- When тренер или администратор отвечает в назначенном треде
- Then создается сообщение, уведомление и при необходимости email

## Discussion reply notifications
- Given публичное обсуждение включено
- When пользователь получает ответ в треде
- Then создается notification типа `discussion_reply`

## Role-based access control
- Given обычный пользователь
- When он обращается к trainer/admin endpoint
- Then доступ запрещен

## Security-sensitive admin actions
- Given администратор выполняет назначение тренера или модерацию
- When действие завершается
- Then создается admin audit log с минимально достаточным контекстом без секретов

## Дополнительная детализация текущего этапа
- Given пользователь заполняет онбординг с полями `preferred_training_style`, `preferred_meal_style` и `hydration_preference`
- When анкета сохраняется и пользователь повторно открывает профиль
- Then сервер возвращает эти поля в `me/profile`, а UI заполняет их без потери значений

- Given администратор просматривает private support ticket
- When он меняет статус тикета и при необходимости переназначает ответственного
- Then новый статус сохраняется, попадает в admin view и действие фиксируется в audit log

- Given администратор просматривает public discussion thread
- When он меняет moderation status на `hidden` или `visible`
- Then статус обсуждения сохраняется, возвращается из admin API и действие фиксируется в audit log

- Given reminder sweep отправил email-уведомление пользователю
- When администратор открывает email logs
- Then список читается из PostgreSQL-проекции и содержит тему письма, тип и статус отправки
